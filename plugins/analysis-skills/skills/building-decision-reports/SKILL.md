# Building Decision Reports

의사결정자가 `그래서 무엇을 알았고, 무엇을 아직 모르며, 다음에 무엇을 해야 하는가`를 한
문서에서 판단할 수 있는 리포트를 만든다. 문장을 꾸미는 작업보다 **증거의 상태, 계산의
재현성, 결론의 강도와 시각적 판독성**이 우선이다.

## 완성 기준

- 첫 화면에서 핵심 결론과 가장 중요한 제약을 이해할 수 있다.
- 관측값, 계산값, 가정, 목표, 해석과 미확인이 서로 섞이지 않는다.
- 모든 비율에는 분모, 모든 시계열에는 기간, 모든 금액에는 기준 단위가 있다.
- 현재 고객 구성과 마케팅 후 시장규모를 같은 것으로 취급하지 않는다.
- 시나리오 계산은 식과 반올림 규칙을 역산할 수 있다.
- 차트만 봐도 계열, 단위, 값, 기간과 핵심 메시지를 알 수 있다.
- 출처와 주의사항이 해당 표·차트 바로 아래에 있다.
- 최종 문서와 모든 시각자료를 실제로 열어 보고 검수했다.

## 작업 흐름

### 1. 요청과 자료의 경계를 고정한다

먼저 기존 보고서, 원자료, 회의록과 관련 정의를 찾는다. 사용자가 지정한 결과물 경로와
기존 편집을 보존한다. 다음을 적어 두지 못했다면 아직 분석을 시작하지 않는다.

- 의사결정 질문과 독자
- 관측 기간과 시간 단위
- 각 지표의 분자·분모·단위
- 고객군이 배타적인지 중복 가능한지
- 코드와 약어의 실제 의미
- 원자료가 말할 수 있는 범위와 말할 수 없는 범위

사용자가 정의를 정정하면 표 한 곳만 고치지 말고 계산, 차트, 캡션, 결론과 후속 요청서까지
그 의미를 전파한다.

### 2. 증거 상태를 분리한다

초안 전에 최소한 다음 상태로 수치를 분류한다.

| 상태 | 의미 | 보고서에서의 처리 |
|---|---|---|
| 관측 | 원자료에서 직접 확인 | 출처·기간·분모 명시 |
| 계산 | 관측값에서 재현 가능하게 산출 | 식 또는 계산 근거 명시 |
| 가정 | 아직 측정하지 않은 입력 | 관측값처럼 서술하지 않음 |
| 목표 | 조직이 선택한 도달점 | 예측과 구분 |
| 시나리오 | 가정에 따른 조건부 결과 | 실제 실적과 구분 |
| 해석 | 관측·계산에서 도출한 판단 | 근거와 대안 해석 명시 |
| 미확인 | 자료 부족 또는 정의 오류 | 빈칸을 추정값으로 메우지 않음 |

고객군·가격·전환·운영량을 분석할 때는
[`references/decision-analysis.md`](references/decision-analysis.md)를 읽는다.

### 3. 결론의 강도를 증거에 맞춘다

현재 표본이 작다는 이유만으로 시장이 없다고 결론내리지 않는다. 현재 채널이나 진료항목이
특정 고객을 거의 유입시키지 않았다면, 확인된 사실은 `현재 자연유입이 작다`이다. 이후
결론은 `제외`가 아니라 가치제안, 획득채널, CAC와 전환율을 검증할 대상일 수 있다.

반대로 패키지를 만들면 다회차가 자동 완주된다고 쓰지 않는다. 계약회차, 예약회차,
완료회차와 환불을 분리한다. 보험유형, 국적, 기존 방문빈도 같은 관측 속성을 지불의사로
대체하지 않는다.

### 4. 계산을 먼저 닫는다

표와 차트를 그리기 전에 원자료 합계와 핵심 파생값을 다른 경로로 재계산한다. 패키지 가격,
필요 계약자, 리드, 예약량과 완료량은 식을 남기고 사람 수처럼 쪼갤 수 없는 값은 목표를
넘기는 최소 정수로 올림한다. 계약액, 실수납과 매출인식은 같은 `매출`로 합치지 않는다.

### 5. 문서를 의사결정 순서로 쓴다

고정 템플릿을 강제하지 않되, 보통 다음 순서가 가장 짧다.

1. 결론형 제목과 한 줄 요약
2. 치명적인 정의·데이터 한계
3. 3~4개의 시각 요약
4. 검산된 사실과 기준선
5. 시나리오와 운영량
6. 전략적 해석
7. 다음 실험, 판단 기준과 필요한 추가 데이터
8. 필요할 때만 방법론·원자료 부록

표나 그림 뒤에는 `자료`, `산식` 또는 `주의`를 바로 붙인다. 독자가 문서 끝의 각주를 찾아야
숫자의 의미를 알게 만들지 않는다. 가능하면 **Markdown 한 파일 + 상대경로 자산 폴더**로
전달한다.

### 6. 차트는 메시지를 정한 뒤 만든다

차트가 하나라도 필요하면
[`references/visual-reporting.md`](references/visual-reporting.md)를 읽고 따른다. 핵심 규칙은
다음과 같다.

- 제목은 주제가 아니라 결론을 말한다.
- 부제는 지표·대상·기간·분모를 말한다.
- 단일 계열은 직접 라벨, 다중 계열은 명확한 범례를 쓴다.
- 범례 순서는 막대나 선의 시각적 순서와 맞춘다.
- 같은 숫자를 범례, 축과 데이터 라벨에 의미 없이 반복하지 않는다.
- 규모 차이가 큰 계열은 독립 패널로 나누고 축 차이를 명시한다.
- SVG에는 `viewBox`, 흰 배경, 대체텍스트용 `title`·`desc`를 둔다.
- 정밀한 숫자 차트는 자동 배치가 불안정한 Mermaid보다 직접 제어 가능한 SVG를 우선한다.

### 7. 렌더링 결과로 검수한다

소스 코드만 보고 완료하지 않는다. 모든 차트를 실제 크기로 렌더링해 다음 순서로 본다.

1. 최대값의 라벨이 잘리거나 겹치지 않는가
2. 기준선과 값 라벨이 충돌하지 않는가
3. 가장 긴 범주명과 범례가 잘리지 않는가
4. 색만 보지 않아도 계열을 식별할 수 있는가
5. 각 값이 어느 계열·단위인지 즉시 알 수 있는가
6. 캡션, 표와 차트의 숫자가 일치하는가

그 뒤 이 스킬의 검증기를 실행한다.

```bash
REPORT_SKILL_DIR="/absolute/path/to/building-decision-reports"
python3 -I "$REPORT_SKILL_DIR/scripts/validate_report.py" path/to/report.md
```

`REPORT_SKILL_DIR`에는 이 `SKILL.md`가 있는 디렉터리를 넣는다. 대상 저장소의 `scripts/`를
잘못 실행하지 않는다.

검증기는 Markdown 이미지 링크, 빈 대체텍스트, 코드 펜스, SVG XML, `title`·`desc`,
`viewBox`를 확인한다. 통과하더라도 시각적 충돌은 잡지 못하므로 렌더링 검수를 생략하지
않는다. 마지막으로 저장소의 일반 검증과 `git diff --check`를 실행한다.

## 인접 스킬과의 경계

- 보건의료 공식 통계의 출처 탐색·연도 정합성·국제 비교가 핵심이면 먼저
  `building-health-evidence-reports`를 사용하고, 최종 의사결정 문서는 이 스킬의 원칙으로
  구성한다.
- 아이디어를 채팅에서 비판만 하는 요청은 `analytique`의 범위다.
- 이 스킬은 조사나 분석을 대신하지 않는다. 확보한 증거와 모델을 **판단 가능한 산출물로
  통합**한다.
